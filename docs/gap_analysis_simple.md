# 系統現狀 vs PRD 差距說明

## 簡單說

收衣、拍照、AI 掃描、客戶簽字這條主線是通的，可以正常用。但 PRD 裡有幾塊沒做，其中有兩三個坑遲早要踩，需要提前知道。

整體大概完成了 60–70%。缺的主要是這幾塊：客戶提異議、操作記錄、多門店、資料匯出。

---

## 已經做好的部分

**訂單和衣物管理**：建單、加衣物、改狀態、取消，都可以用。付款方式和折扣這塊甚至比 PRD 要求做得還多一點。衣物可以按件計費、記材質、記服務類型，夠用了。

**拍照和上傳**：支持正面、背面、細節特寫、領口、袖口、下擺六個角度。照片上傳後會自動判斷是否模糊或過暗，有問題當場提示，讓員工重拍。

**AI 驗衣**：接的是 GPT-4.1 Vision。拍完照後點「識別」，AI 會在照片上畫框，標出污漬、破洞、缺扣這些問題的位置和嚴重程度。員工可以手動刪掉誤判，或者補錄 AI 沒識別到的問題。

**客戶簽字**：訂單驗衣完可以生成一個鏈接和二維碼，客戶用手機掃一下就能看到帶標注的驗衣照片，看完可以直接在手機上手寫簽字確認。

**打印**：驗衣報告和收款收據都有打印頁，瀏覽器直接 `Ctrl+P` 就能出紙。

**後台管理**：獨立的管理後台，可以查所有訂單、客戶，管理員工賬號（新增、改密碼、刪除）。

**手機安裝**：在 iPhone 上可以把這個 App 安裝到主屏幕，用起來和原生 App 差不多。

---

## 缺的東西，按重要程度排

### 需要盡快補的幾個問題

**客戶沒有提異議的入口。**
PRD 裡設計了一個「有異議」的選項，客戶有疑問可以填寫，訂單進入爭議狀態由店長處理。這塊現在完全沒有——客戶掃碼只能「確認」，遇到糾紛只能線下口頭溝通，什麼記錄都留不下來。這是最需要補的功能之一。

**AI 識別結果刪了沒有記錄原因。**
PRD 要求員工刪除 AI 發現的問題時，必須說明為什麼刪（比如「光線陰影，不是污漬」）。現在直接刪，日後客戶說「你們當時明明說有問題，後來又不算了」，系統拿不出任何說明。

**客戶簽完字，訂單記錄還能改。**
按說客戶簽字後驗衣結果就應該定下來。但現在缺少快照機制，員工還可以繼續修改問題。萬一出了糾紛，客戶說「我簽字的時候不是這些問題」，系統拿不出當時的版本。

**系統只有 UUID，沒有訂單號。**
現在訂單 ID 是一串 UUID（`3e4a9c21-...`），沒有可讀的訂單編號。跟客戶溝通根本沒法報這個號。PRD 設計的格式是 `ORD-20260426-0001`，做起來不複雜，但現在沒有。

**AI 識別完不需要確認就能推進狀態。**
PRD 說 AI 跑完之後，員工必須手動確認一遍才能往下走。現在這個卡點沒有，可以直接跳過確認步驟。

---

### 不急，但要記在清單裡

照片上傳時計算了清晰度和亮度分數，但這個分數沒存進資料庫，用完就丟了，以後沒辦法查哪批照片質量有問題。

客戶開沒開那個簽字鏈接，系統一概不知道。PRD 要求記錄 `viewed_at`，現在完全沒有。

客戶確認鏈接一生成就永久有效，建議加個過期時間（比如 72 小時），現在是個安全隱患。

操作記錄幾乎是空的。PRD 要求誰在什麼時間做了什麼都要記錄，現在只有「問題被改了哪個字段」的歷史，建了訂單、上傳了照片、改了狀態——全沒記。

照片目前可以不登錄直接訪問（只要猜到文件名）。比較正確的做法是加個訪問鑑權或短期簽名 URL。

---

### 暫時不考慮的

多門店、中層店長角色、CSV 匯出、洗後複檢對比、統計報表——PRD 都有提，但目前是單店使用，這些等以後規模擴大再說。

---

## 角色設計的差距

PRD 設計了四個角色：店員、店長、後場人員、管理員。

現在只有兩個：普通員工（`staff`）和管理員（`admin`）。店長這個中間層沒有，後場人員也沒有。如果要做多人分工和分級管理，這塊要補。

---

## 資料庫裡缺的字段

| 缺少的字段 | 有什麼影響 |
|---|---|
| 訂單號 order_no | 跟客戶溝通時拿不出一個好記的單號 |
| 門店 ID store_id | 要做多門店的話必須加 |
| 奢侈品標記 luxury_flag | 高價值衣物沒有特別提示 |
| 建單人 created_by | 不知道哪個員工建了這個訂單 |
| 預計完工日 expected_finish_date | 客戶不知道什麼時候能來取 |
| 圖片質量分（入庫）| 現在只在上傳時顯示，沒存下來 |
| 客戶查看時間 customer_viewed_at | 不知道客戶有沒有打開確認頁 |
| 異議原因 dispute_reason | 還沒有這個功能，字段也沒有 |

另外，每個驗衣問題（`inspection_issues`）缺一個狀態字段，PRD 設計了「建議中 / 已確認 / 已拒絕」三個狀態，現在只能存或刪，AI 發現的問題和員工確認過的問題混在一起沒有區分。

---

## 說在最後

這個系統拿來跑日常收衣和驗衣完全沒問題，客戶查看和簽字的流程也是通的。

最大的隱患是：出糾紛時系統能提供的記錄很少。沒有完整的操作日誌，客戶無法提異議，簽字後記錄還能改——這三個問題優先解決，其他的可以排後面。
